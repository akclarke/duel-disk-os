1. Executive Summary

This document compares the current Duel Disk OS implementation against the official Yu-Gi-Oh! TCG rules. Twelve rule systems were audited. Five are MISSING entirely, five are PARTIAL, and two are PRESENT in simplified form.

2. Detailed Findings

2.1 Chain Stack & LIFO Resolution — MISSING

Official Rule: When a card or effect activates, each player may add to the chain in turn-player-goes-first order. The chain resolves Last-In-First-Out (LIFO). Each link must meet the Spell Speed requirement of the preceding link.
What exists: Core.Effect.activate() immediately executes effect.operation(freshEnv) inside a setTimeout(400ms). There is no chain stack data structure, no opportunity for either player to respond before the effect resolves, and no LIFO unwinding.

Specific code location: src/Core/Effect/index.js lines 55–111 — the entire offline execution path runs a single effect synchronously with no chain interlude.

Impact: Every effect that should be chainable (Quick-Play spells, trap activations, Quick Effects) resolves before the opponent can respond. Counter traps, Solemn cards, and negation effects are mechanically impossible to use in response.

2.2 Spell Speed 1 / 2 / 3 Enforcement — MISSING

Official Rule: Spell Speed 1 = Normal Spells, ignition monster effects. Speed 2 = Quick-Play Spells, Traps, Quick Effects. Speed 3 = Counter Traps only. You may only chain a card/effect of equal or greater speed to the preceding chain link. Speed 1 cannot be chained to anything.
What exists: CARD_TYPE in src/Components/Card/utils/constant.js defines SPELL.QUICK, TRAP.COUNTER, etc., but there is no spell_speed property on any effect object, card definition, or factory wrapper. No enforcement mechanism exists anywhere in the codebase.

Specific code location: src/data/effectFactory.js — none of the wrappers (onActivate, onAttackDeclared, oncePerTurn) assign a spell speed. No lookup table maps card types to speeds.

Impact: Normal Spells can chain to Counter Traps. Counter Traps can be activated during Main Phase with nothing to chain to. Spell Speed 1 monster effects can be added to chains.

2.3 Priority Window Between Players — PARTIAL

Official Rule: After a card or effect resolves, both players receive a Priority Window to activate effects. The turn player receives priority first. If neither player wishes to activate anything, the game state advances.
What exists: CPUPlayer._tryNormalSummon() calls offerChainToPlayer() after the CPU performs a Normal Summon — this shows the player's face-down traps in a modal window. This covers exactly one trigger window (opponent Normal Summon) but nothing else.

What is missing:
  • No priority window after CPU activates a Spell card
  • No priority window after the player activates an effect (CPU cannot respond)
  • No priority window at the start of each Phase (e.g., Standby Phase effects)
  • No priority window after damage calculation in the Damage Step
Specific code location: src/AI/CPUPlayer.js lines 24–33 — offerChainToPlayer() is only called from _tryNormalSummon(), not from any other action.

2.4 SEGOC (Simultaneous Effects Go On Chain) — MISSING

Official Rule: When multiple triggered effects meet their trigger condition simultaneously, they all go on the chain in the following order: (1) Mandatory turn-player effects → (2) Mandatory non-turn-player effects → (3) Optional turn-player effects → (4) Optional non-turn-player effects. Each player chooses which of their own effects to chain first.
What exists: fireTrigger() in src/data/triggerRegistry.js runs each matching trigger in a separate setTimeout(500ms), firing them sequentially and independently.

Specific code location: src/data/triggerRegistry.js lines 110–151 — the for (const trigger of triggers) loop fires each trigger in its own setTimeout with no grouping, ordering, or player choice.

Impact: When two cards would simultaneously trigger (e.g., Witch of the Black Forest destroyed at the same time as Sangan), their operations fire 500ms apart in definition order rather than being placed on a single chain and resolved LIFO.

2.5 Effect Negation Mid-Chain — MISSING

Official Rule: A negation effect (Counter Trap, Solemn Judgment, etc.) placed higher on the chain than a target effect will negate that effect when the chain resolves. The negated effect does not resolve; its declared targets are still selected but have no action applied to them.
What exists: No negate() primitive in effectFactory.js. Cards like Legendary Six Samurai - Shi En are implemented by directly destroying the opponent's Spell/Trap card from the field — this is "destroy" not "negate." The chain stack does not exist, so there is nothing to negate.

Specific code location: src/data/effectsRegistry.js — Shi En (29981921) entry calls destroyMonsters rather than having any negation primitive.

Impact: Negation cards cannot function as intended. Cards like Solemn Judgment (cannot be registered), Effect Veiler (no timing), Forbidden Lance (no ATK modification + negation pattern) are structurally impossible to implement.

2.6 Once-Per-Turn Tracking (Per Duel) — PARTIAL

Official Rule: "Once per turn" limits reset at the start of each turn (Draw Phase). "Once per duel" limits (Wind-Up single-use) never reset for that copy. If a card returns to hand/deck and is re-summoned, its OPT resets because it is treated as a new instance.
What exists: Two separate mechanisms:
  • sessionStorage keyed by once_per_turn_{unique_count} — cleared in Game.jsx on every turn change
  • cardEnv.wind_up_used = true — permanent flag on the cardEnv object, never reset
What is wrong:
  • sessionStorage persists across browser sessions (not scoped to a single duel)
  • If a card is returned to hand (e.g., via Zenmairch) and re-summoned, it gets a new cardEnv object with a new unique_count, so its OPT tracking resets — this is actually correct by TCG rules but happens accidentally
  • wind_up_used is set on the cardEnv directly; when the reducer calls applyPassiveEffects, it gets a shallow copy from Redux ({ ...environment }), which means wind_up_used may be lost on the next state update for cards in some zones

2.7 Target Declaration & Target Locking — MISSING

Official Rule: Targeting happens at activation — the player declares targets when they put the effect on the chain. If a declared target is no longer a valid target when the effect resolves, the effect disappears without resolving (most cases). Targets are "locked" and cannot be changed after activation.
What exists: All card selection (openSelector) happens inside effect.operation(), which runs at resolution time — not at activation time. There is no declared_targets array on chain links, and no validity check when the operation finally resolves.

Specific code location: Every oncePerTurn, onActivate, and hand-written effect that calls openSelector does so inside the operation function, not in a separate pre-chain target phase.

Impact: A player can activate an effect targeting a monster, the opponent can "destroy" that monster on the chain, and the player's effect will still resolve against the now-absent monster (or throw a silent error when the UID lookup returns -1).

2.8 Cost vs Effect Separation — MISSING

Official Rule: Costs are paid at activation, before the chain is built. If the effect is negated, the cost has already been paid and is not returned. Costs include: discarding, tributing, paying LP, detaching XYZ materials, banishing from GY.
What exists: Costs and effects are merged into a single operation(env) function. For example, Gagaga Cowboy detaches a material AND deals damage in the same async function. Predaplant Chimerafflesia selects a card to banish AND discards in the same function.

Specific code location: src/data/effectsRegistry.js — every hand-written operation function performs costs inside the operation body (e.g., material splice inside Zenmaiday's field_activate, LP payment inside Dark Magic Curtain's operation).

Impact: If a cost-paying effect were negated (once negation is implemented), the cost would be reversed since the entire operation would not have run. All cost-paying effects need to be refactored into a two-phase cost(env) → chain builds → operation(env) structure.

2.9 Replacement Effects ("Instead" Clauses) — PARTIAL

Official Rule: Replacement effects use "instead" or "cannot be X, you can Y instead" language. They replace the default outcome of an event (e.g., destruction) with a different outcome. They are not activated; they apply automatically when the event would occur.
What exists: The can_protect_from_destroy / protect_from_destroy hook on card objects, checked inside Core.Battle.battle_to_graveyard(). Wind-Up Zenmaines uses this. Toon Kingdom has its own manual check in the same function.

What is missing: The hook is only checked in battle_to_graveyard() (battle destruction). It is not checked in:
  • effectFactory.destroyMonsters() — card effect destruction
  • effectFactory.makeDestroy1Effect()
  • Any hand-written destroy operation in effectsRegistry
Replacement effects for other events (e.g., "instead of being sent to GY, banish it" for Macro Cosmos) are entirely absent.

2.10 Damage Step Activation Restrictions — PARTIAL

Official Rule: During the Damage Step, only specific cards can be activated: cards that modify ATK/DEF, mandatory triggered effects, cards that specifically say "during the Damage Step." Quick-Play Spells, Traps, and most Quick Effects cannot be activated during the Damage Step.
What exists: BATTLE_STEP.DAMAGE_STEP is defined in src/Components/PlayerGround/utils/constant.js and tracked in battleMetaReducer. The trap activation window in Field.jsx only opens at START_STEP, not DAMAGE_STEP — so most traps are effectively blocked from the Damage Step already.

What is missing: No general enforcement. A player could click on a face-down Quick-Play Spell during the Damage Step and activate it without restriction (Side.jsx only checks is_main_phase, not whether we are in a battle step). ATK/DEF modifying effects should be allowed in the Damage Step but are not tagged as such.

2.11 Missing the Timing Rule — MISSING

Official Rule: An optional trigger effect that uses "When [trigger]: you can [effect]" can only be activated if the trigger condition was the last thing to happen. If another event occurred after the trigger (e.g., another effect resolved), the optional trigger "misses the timing" and cannot be activated.
What exists: All triggers in triggerRegistry.js fire via fireTrigger() immediately when their condition is met, regardless of what happened afterward. There is no tracking of "last event" and no check against it.

Impact: Optional trigger effects (e.g., "When this card is destroyed: you can add 1 card to your hand") will always activate even when they should miss the timing. In practice, this makes effects slightly more powerful than the TCG rules allow, but rarely causes game-breaking errors for casual play.

2.12 Mandatory vs Optional Trigger Ordering — PARTIAL

Official Rule (SEGOC follow-up): When simultaneous triggers fire, mandatory effects (those that say "X happens: do Y" without "you can") must be chained before optional ones ("X happens: you can do Y"). Mandatory triggers cannot be declined.
What exists: All triggers are treated as optional. The fireTrigger loop fires each matching trigger with a setTimeout(500ms) delay, with no distinction between mandatory and optional effects.

What is missing: No mandatory: true flag on trigger entries. No ordering enforcement when multiple triggers fire simultaneously.

Impact: Mandatory triggers (e.g., Witch of the Black Forest — "is sent to the GY: add 1 monster to your hand") are treated as optional and fire asynchronously 500ms after the event. In practice, since no UI prompt exists, they always activate, which accidentally gives the correct result even without formal enforcement.
